# Phase 5 — performance (Checkpoint B)

Date: 2026-11-27. Software optimizations are implemented and verified for pixels; a **partial ESP32
measurement** was taken during the diagnostic campaign (Buddy offline only). The six-screen matrix
was not measured because the MOCK bench image was not flashed. **Phase 5 is closed on software;
the full hardware matrix is deferred to Phase 6** on a native physical host. No 50 ms target is
claimed.

## 1. Baseline (Phase 4 diagnostic image, 45 samples)

| Screen | FPS | Render avg | Render max |
| --- | --- | --- | --- |
| Buddy EN/FR/DE | 20 | 47.4–48.2 ms | 47.9–48.6 ms |
| Session | 8 | ~100 ms | ~100 ms |
| Tokens | 8 | 89–90 ms | 90 ms |
| Tools / MCP / System | 8 | ~33 ms | 33 ms |
| Quiet Buddy | 4 | 47.7 ms | 47.9 ms |

The frame push of the 220×220×16-bit sprite at 27 MHz is ~29 ms; the rest is render work. Session and
Tokens carry 36 and 28 tick arcs; Buddy carries 2 face arcs.

## 2. Root of the cost

`fillEllipseArc` (LovyanGFX) scans the **full radius bounding box** row by row with per-pixel slope
tests. A 2° tick at r=100 therefore pays for a ~200-row scan. 36 + 28 calls per frame explain the
50–60 ms gap between Buddy and the two dashboards. Measuring text called `textWidth()` once per
character and the truncation loop removed one character and re-measured the whole string (O(n²) for a
long model/agent).

## 3. Changes

1. **Tick span tables** (`firmware/src/TickTables.h`, generated by `tools/ui-preview/gen_ticks.cpp`):
   the exact `fillArc` pixels of each tick are stored as horizontal spans. Per frame, Session draws
   160 spans and Tokens 312, with `drawFastHLine`; the face keeps `fillArc`. This removes 64
   full-radius scans per frame without changing one pixel.
2. **Text measurement**: ASCII strings use one `textWidth(value)` call (the common case); composed
   Latin-1 accents keep the per-codepoint sum. `text()` measures once per font level instead of twice.
3. **Truncation**: binary search over codepoint boundaries (≤7 measures for a 92-byte string) instead
   of the O(n²) loop.
4. **`number()`** moved to a LovyanGFX-free `Format.cpp` and covered by host boundary tests; the
   formatting is unchanged.

Flash/RAM delta of the whole RC vs the 4.1 release: **+2 048 B flash** (378 782 vs 376 734),
**+16 B RAM** (22 620 vs 22 604). The tick table is flash-only; the text path adds ~96 B of stack.

## 4. Expected effect (partially measured)

The arc work is replaced by a bounded number of span writes (~472 calls; the pixels are the same as
before). The push floor (~29 ms) and the rest of the drawing remain. Buddy was measured once on the
real ESP32 (section 6); Session/Tokens were **not** measured in a stable scenario, so the 50 ms
target is not claimed.

## 5. Measurement plan (requires flash approval)

1. Flash the diagnostic LIVE image (`3646d4ce…`) or the RC (`dd7d1d57…`) — the diagnostic exposes
   `render_avg_us`, `render_max_us`, heap and TX counters every 5 s; the RC does not.
2. For each screen, English/French/German, take 45 samples in steady state; record the median, P95,
   max and the maximum interval between USB service calls.
3. Compare with the baseline above; verify no USB starvation (bridge ACKs, no RX overflow).
4. Re-run the six-screen visual check on the panel (the preview equivalence does not prove the
   panel).

The desktop preview timing is **not** used as ESP32 evidence.


## 6. Hardware measurement — Buddy (fix3 diagnostic, 2026-11-27)

The fix3 diagnostic image (`3689b828…`) ran on the ESP32-C3 while the USB handshake was failing. The
device stayed on the Buddy screen (offline, no host), so this is a **single-screen, offline** sample,
not the planned six-screen matrix:

| Metric | Value |
| --- | --- |
| Render average (5 s window) | 46 601 µs |
| P50 / P95 / P99 (1 ms histogram) | 46 000 / 46 000 / 46 000 µs |
| Max | 46 630 µs |
| FPS window | 3–4 (offline Buddy interval, not a LIVE FPS claim) |
| Free heap / minimum / largest block | 244 100 / 244 100 / 221 172 B |

The Phase 4 baseline for Buddy EN/FR/DE was 47.4–48.2 ms average and 47.9–48.6 ms max. The offline
Buddy sample is therefore consistent with a small improvement, but it is not a controlled before/
after comparison: the screen was offline and only one screen was sampled. **Session and Tokens were
not measured on hardware**; the 288-image preview equivalence proves the pixels, not the timing.

The six-screen matrix (3 languages, 6 screens, quiet Buddy, p50/p95/p99, heap, USB gap, drops) needs
the MOCK bench image with the final fix and explicit flash approval. It remains an open gate. No
hardware timing is claimed for Session/Tokens.
